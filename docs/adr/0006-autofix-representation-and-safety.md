# ADR-0006 — Auto-fix representation and safety strategy

**Status:** Accepted
**Date:** 2026-07-26
**Decision makers:** claude-sonnet-5 (P2-06 implementation), recorded per the escalation rule (a decision touching more than one package's public API)

---

## Context

P2-06 added `argus fix`: an `--dry-run`-capable command that applies mechanical edits for violations that offer one, then runs the touched file through Prettier. This is the CLI's first mutating command, and the phase doc calls it "the riskiest part of this phase" — round-trip safety (comments and significant whitespace never destroyed; `fix` then `check` shows no violations) is non-negotiable, not a nice-to-have.

Several cross-package decisions had to be made together: how a rule expresses "here is a safe edit", how that edit survives from a rule's `create()` closure through the engine to `apps/cli`, what happens when two violations propose overlapping edits, and where Prettier fits architecturally given it is the first external tool this repo calls programmatically rather than as an arm's-length subprocess. None of these are visible from any single package's diff, which is what puts this ADR in scope rather than a `.work/` note.

Investigated first and found to be true, not assumed: nothing fix-related existed anywhere in the codebase before this task (greenfield at the type/port/package level), and of the ten built-in rules, only `style/import-order` is realistically auto-fixable under a "formatting only" scope — the other nine need a semantic judgement call (renaming with every reference tracked, splitting a long function, writing real documentation) that no mechanical transform can safely make.

## Decision

1. **`Fix` is a new domain type**, `{ position: Position; replacement: string }`, smart-constructed and frozen like every other domain value (`packages/core/src/domain/fix.ts`). It is threaded additively: `RuleReport.fix?` → `CapturedReport.fix?` → `Violation.fix?`. No port signature changed — `RuleRunnerPort.run` still returns `Result<readonly Violation[], RuleExecutionError>`. A rule reports a fix the same way it reports a message: `context.report({ message, position, fix })`.

2. **A rule offers a fix only when it can prove the specific case is safe — never as a best-effort guess.** `style/import-order`'s fixer withholds the fix when: the run of imports it would reorder contains anything other than `import_statement` nodes; a comment **abuts** the block with no blank line between them — on the first/last import's own line, or the line directly above/below (outside the contiguity window, but reordering would still leave it describing a different import); any import is **side-effect-only** (`import "./polyfill.js";` — its contract is _when_ it runs relative to the others, so a cross-group move is precisely the breaking change); or two imports share one line (the whitespace between them is unreconstructible, since a rule sees only the AST — `AstNode` never exposes raw source or byte offsets, a P1-03 scope limit this ADR does not revisit). A violation with no fix is still reported; under-fixing a case that cannot be proven safe is always preferred over a wrong edit. Gaps between reordered imports are reconstructed from line numbers alone (`"\n".repeat(nextLine - prevLine)`), reused **positionally** (the gap between original positions _i_ and _i+1_ separates whatever ends up at sorted positions _i_ and _i+1_) rather than reattached to specific statements, because there is exactly one fewer gap than there are imports.

   > The last two conditions were added after the independent review (#39 HIGH-3, MEDIUM-1) reproduced both: a trailing `// keep this next to fs!` silently reattaching to a different import, and `import "./setup-globals.js"` being hoisted below `express`. The original scoping argument — "we only move imports _between_ groups, never _within_ one, so order is preserved" — is **inverted** for side-effect-only imports, which is what made that case easy to miss.
   >
   > A **follow-up review then found the comment condition itself under-inclusive** (HIGH-1): it guarded the import's _own_ line but not the line directly above it, which is where every line-scoped directive comment lives — `eslint-disable-next-line`, `@ts-expect-error`, `biome-ignore`, `prettier-ignore`, `istanbul ignore next`. Those bind to the next line by definition, so reordering below one moves a _suppression_ onto a statement that never needed it. Reproduced end-to-end: a project that compiled at `tsc` exit 0 came back at exit 2 after `argus fix` (`TS2578` on the newly-covered import plus the original error resurfacing), while `argus` itself reported success. The guard is now "no blank line between comment and block" in either direction; a blank line is what marks a comment free-floating rather than attached. Worth noting how it survived the first review: a passing test **asserted** the permissive behaviour, justified by the one benign example it used (`// module docs`) — the generalisation from that example to "a comment on a separate line is not attached to any one import" is what was false.

3. **Conflict resolution is the applier's job, not the rule's.** `apps/cli/src/apply-fixes.ts` de-duplicates fixes by structural equality (a rule may attach the identical edit to every violation it resolves at once) and, for two different edits that still overlap after de-duplication, keeps the earlier-starting one and drops the rest. A rule never needs to reason about what else might be reported in the same file. "Overlap" is judged on the ranges themselves: a zero-width insertion at offset _N_ and a replacement starting at _N_ do **not** overlap — `magic-string` composes `appendLeft(N)` with `overwrite(N, …)` cleanly — so both apply. Only a second _insertion_ at an already-taken offset is dropped, which is the ambiguous case #39 LOW-2 identified (the follow-up review's LOW-1 was this guard over-reaching to the replacement case and silently discarding a safe fix).

4. **Prettier is a whole-file finishing pass over files `fix` actually touched — never a repo-wide reformat.** `import-order`'s fix mechanically splices text; Prettier then normalises the result, which is what the phase spec's "delegated to Prettier for formatting rules" buys even for a non-formatting rule's fix. A file with zero applied fixes never reaches the formatter.

5. **Prettier is called programmatically, behind a new port (`FormatterPort` in `@argus/core`), implemented by a new package (`@argus/adapters-prettier`) — not a direct import from `apps/cli`, and not an arm's-length subprocess.** Every existing external-tool integration in this repo goes through a port (`AstParserPort` ← `TreeSitterAstParser`; the unimplemented-but-already-defined `ToolAdapterPort` and repository ports sketched ahead of their phases), and `docs/plan/01-repo-structure.md` already names `packages/adapters/prettier/` as this exact tool's home — the location is documented intent, not invention. ADR-0002's copyleft-isolation rationale for running tools as subprocesses does not apply here: Prettier is MIT-licensed and already a root devDependency; the port exists for the same reason every other one does (a contract test validates the real adapter in isolation; a fake remains available to any future caller), not for licence containment.

6. **The adapter resolves Prettier config relative to the project root it is constructed with, never `process.cwd()`.** `argus` can run from a subdirectory of the project it scans — `PrettierFormatter`'s constructor takes the project root explicitly and resolves every file against it before calling Prettier's API, avoiding the same class of bug P2-02 already fixed once for `ignore:` globs matching against the wrong base directory.

7. **Exit codes reinterpret `check`'s 0/1/2 differently for `--dry-run` versus a real run**, because the two modes answer different questions and one meaning would make one of the flows useless for CI: a real run reports **state** (`0` = no violations remain once the run finished), extending `check`'s own "violations exist" contract to "after fixing what I could". `--dry-run` reports **what an action would do** (`0` = fix would change nothing), the same idiom as `prettier --check`/`terraform plan`, because it cannot promise the repo would end up clean without writing anything.

8. **The run is two-phase, and its "state" claim is measured rather than inferred.** Every file's fixed text is computed and formatted before _anything_ touches disk, so an **analysis** failure on a later file cannot leave earlier ones already rewritten (#39 HIGH-2 — the first implementation wrote as it went and contradicted the documented "nothing is written when a scan can't complete"). And `remaining` is derived by **re-running the rules over each fixed file's text**, not by counting splices attempted — a fixer whose edit fails to resolve what it claimed would otherwise let exit `0` assert a cleanliness nothing ever checked (#39 MEDIUM-5).

   > The follow-up review (MEDIUM-1) found that claim stated too broadly: phase two had no error handling at all, so an **environmental** write failure — read-only file, full disk — still left the run partially applied, and escaped to `main`'s last-resort handler as a bare `unexpected error: EACCES …` with no summary and no per-file context. Two-phase buys atomicity against everything _computable_, not against the filesystem; N-file atomicity would need temp-write-and-rename with rollback, which is not worth it here. So the commit phase now reports each failed write in the CLI's own voice, finishes the remaining writes rather than stranding more files, still prints the summary of what did land, and exits `2`. `remaining` is measured against what actually reached disk, so an unwritten file keeps its violations instead of being credited as fixed.

9. **A fix's offsets come from the bytes read off disk, never from `parsed.root.text`.** Tree-sitter's `program` node starts at the first token, so any file beginning with a blank line, space, tab, or BOM has a root whose text is a _truncated_ copy of the source while every `Position` stays absolute. `#39 HIGH-1` reproduced the consequence: a comment deleted, an import duplicated, and exit `0` while the violation survived. `ParseOutcome` now carries the exact source per file, and `parseAll` is its single producer.

## Consequences

### Positive

- Adding fix support required no changes to `RuleRunnerPort`, `Engine`, or `Runner`'s public contracts — every existing rule and every existing consumer of `Violation[]` is unaffected.
- The safety-over-coverage rule (decision 2) means `argus fix` can never be the cause of a lost comment, a corrupted file, or a directive comment silently changing what it suppresses; the cost is that some real-world import blocks (ones with a comment flush against the block, or a same-line pair) will not be auto-fixed and still need a human.
- The port precedent (decision 5) means a second fixable rule that needs a genuinely different external formatter, or a test that wants to fake Prettier's behaviour, has a contract to conform to rather than a bespoke integration to invent.

### Negative

- Only one rule is fixable this task. The fix engine's generality (conflict resolution across multiple different fixes in one file, the `FormatterPort` abstraction) is proven correct by test but not yet exercised by a second real fixer — revisit if that generality turns out to be wrong-shaped once one exists.
- `--dry-run`'s exit code answering a different question than a real run's is a deliberate, documented asymmetry, but it is still an asymmetry a new contributor has to learn once (mitigated: spelled out in `docs/guide/cli.md`, `apps/cli/README.md`, and this ADR).
- Decision 8's re-verification re-parses and re-runs the rules over every changed file, so a run that fixes a lot of files pays roughly double the analysis cost on those files. Accepted deliberately: a mutating command's exit code is a CI contract, and a cheap-but-unfounded claim is worse than an honest cost.
- The four decline conditions in decision 2 are **sufficient, not provably complete** — they are the cases we found, and three of the four owe their current shape to a reviewer going looking. Two successive reviews each widened the comment condition, the second because the first's fix was itself under-inclusive; a fifth shape of unsafe reorder probably still exists. The mitigation is structural rather than analytical: declining is cheap and always safe, so the bar for adding a condition is deliberately low.
- Widening the comment condition to "no blank line between" costs real fix coverage: a file whose imports sit flush under a header comment — a common layout — is no longer auto-fixable, and the only way to distinguish that header from a directive is a comment-text allowlist we deliberately did not build (`eslint-`, `@ts-`, `biome-ignore`, … would go stale silently, which is the same failure mode one level up). Accepted: the user sees the violation and fixes it by hand, which is the documented under-fix outcome, not a wrong edit.
